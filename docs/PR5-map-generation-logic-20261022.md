# PR5 地图生成逻辑修复（2026-10-22）

用户指出重复照明与房间中央的门洞。先前将它们改成设施标签，只解决可读性，未解决生成错误，不能作为地图验收通过的依据。

## 原因与修复

- 本空间任务只发送陈设数量；子图模型看不到父图已登记的陈设身份。现在发送 `spaceSize.furnishingInventory` 的 ID、类型、名称、尺寸与真实物品支撑引用。父图、子图均校验既有账本；新身份需明确 `additional=true`，不按名称合并，也不会吞掉确实同名的两件物品。
- 门洞被作为普通 `contents` 排进房间内部。现在旧门洞提示仅记录到结构门的来源中，不再生成独立家具 body。新任务要求门由程序根据房间边界与已有连接生成。
- 通用走廊模板将直接相通的大厅和厨房分到走廊两侧。现在读取同图房间间的 `door`、`adjacent`、`estimated` 开放路线，让相连房间共墙并生成一对同位置的门侧记录。行走路径沿实际门拓扑计算。容量或锁约束无法满足时保留原图并报告冲突，不用假走廊冒充连通。
- 子图继承父图同一墙面的门，门方向参与通行净空与碰撞检查；父图门变化会同步已有子图。显式删除陈设也会同步父图投影，避免被旧父图约束复活。尺寸变更仍经父子原子闭包统一处理。
- 真实样本中的 3×1 米工作台不能通过固定墙中央门位完成摆放。求解器增加有限的合法门位候选，再检查家具、门扇与实际通行；子图继承父图的陈设坐标，避免用另一套摆放把同一张工作台挤掉。已经校验的未落位约束 ID 可以继续重试。
- 普通地点类型的入口与室内房间之间的已登记连接同样参与拓扑，避免入口成为孤立走廊支路。新估计家具不再登记到包含下级空间的容器轮廓；已登记物品的真实归属与明确新增仍保留。模型同时收到下级空间的 `detailScope` 与旧重复投影的显式清理规则。
- 两种渲染器支持东西墙门；同一开口的两侧只画一次。POV 保留墙面方向，同时继续剥离私有路线 ID 与陈设来源。
- 布局策略指纹升至 `layout-v12`，旧布局可进入正常重新生成流程。

## 验证

回归包含真实生成器与真实 SQL 候选事务：12×8 大厅与 4×3 厨房共墙；父子入口一致；通行路径经过真实门；厨房不缩小操作台即可容纳柜架；换视图不能换 ID 再造灯；明确新增允许同名物品；门变化与显式删除跨父子图同步；失败保留旧场景；POV 不泄漏私有字段。

全量测试 **2380/2380**；类型检查与打包通过。根目录 `dist/` 是安装单元，随源码同步构建。
