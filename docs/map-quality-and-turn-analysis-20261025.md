# 地图质量研究与逐轮调用分析（2026-10-25）

## 本次结论与范围

优先目标是空间逻辑、可用布局与展示质量。当前不以 token 或提示词字数作为优化目标；用户已有的工作分批数、额外请求额度、连接输出上限和超时继续生效。

本次完成调用链研究和逐轮分析导出。地图生成流程、布局算法和用户提示词预设尚未更换，也未增加地图生成的模型阶段。开源组件仍为候选，未安装到运行包。离线测试不代表外部模型质量已经改善。

研究覆盖 main `a49dcd2` 与地图层级修复草稿 PR #8 `4f51314`。本次日志与研究交付叠加到 PR #8，保留其楼层导航、主房间可用地面和真实城市轮廓修复。

## 地图质量的核心缺口

| 环节 | 当前实际能力 | 优先研究的缺口 |
| --- | --- | --- |
| 资料依据 | `atlas-layout-evidence.ts` 先选择原文片段，再交布局；片段有来源与偏移验证 | 片段尚未统一表达包含、楼层、方向、直接入口与可通行关系；不能只让后续模型自行理解散文 |
| 室内规划 | `atlas-sql-layout-task.ts` 下发尺寸、账本、锁与 rooms；`generation.mjs` 接入已登记连接；`room-topology.mjs` 求共墙 | 模型请求主要表达 w/h/side；方向、私密空间的入口限制和功能分区缺少完整契约。不能认为现有程序完全没有连通求解 |
| 城市规划 | districts 使用 bank/order；真实建筑有归属与宽高；无依据河流默认零 | 东西分组与序号表达不了完整的城市空间关系。需要父图继承、真实道路关系与多方向约束 |
| 验收 | `assessMapCompleteness` 区分合法场景、缺项、尺度、输入对齐；已有几何与锁校验 | 合法 JSON、合法场景、地图完整和美观分别验收；必须增加有依据的空间关系满足率 |
| 显示 | Canvas、层级切换、HUD 收纳、皮肤；PR #8 补楼层与空间入口 | 不同层级的标签、人物、家具和道路要有明确展示责任；评测需要固定相机与缩放 |

“相邻”与“能够穿门进入”必须分开。“同一建筑”“同一楼层”“同一房间”也必须分别表达。不能凭名字把未知归属的房间搬到某层，也不能为了布局成立，添加本来没有的道路、门或实体。

## 建议的空间规划契约：space-plan/v1（提案，尚未接入）

先扩展现有证据提取与布局输入，不先增加一个独立的逐图模型调用。证据提取仍按用户设置合批，地图规划仍按用户设置合批。

每条空间关系至少包含：

| 字段 | 语义与检查 |
| --- | --- |
| `mapRef`、`fromRef`、`toRef` | 冻结目录内的真实引用；局部家具标识另设命名空间 |
| `relation` | `contains`、`same-floor`、`east-of`、`north-of`、`adjacent`、`accessible-via` 等明确枚举；相邻不隐含门 |
| `evidenceRefs` | 已验证原文片段编号；不能引用另一本批次不存在的编号 |
| `basis` | `source` / `author` / `estimate`；源文有描述不等于几何已实测 |
| `strength` | 必须满足的明确约束与可调整的排位偏好分开；未知不强行补全 |
| `confidence` | 用于解释估计，不允许用高置信度覆盖作者锁或绕过引用校验 |

资料中出现层级冲突时，空间规划只报告问题；地点归属的更新仍走世界建设操作和事务，不允许绘图阶段偷偷改 SQL 实体树。

模型职责：解释有依据的关系、用途与合理陈设。程序职责：引用、尺度、锁、包含、共墙、开门、碰撞、净空与导航。对没有依据的布置可生成多个本地候选，先淘汰违反硬约束的候选，再比较功能合理性、通路长度和画面清晰度。装饰分数不能抵消漏画空间或堵门。

## 开源候选与当前选择

以下功能以官方资料核对；适配结论是本项目的工程判断，尚未声称已经接入或通过酒馆实测。

| 项目 | 能力 / 许可证 | Atlas 的适配结论 |
| --- | --- | --- |
| [Z3](https://github.com/Z3Prover/z3) | 约束求解；MIT | 可先离线验证尺寸、方向、不重叠等可满足性。官方 [JS 说明](https://github.com/Z3Prover/z3/blob/master/src/api/js/PUBLISHED_README.md) 明确线程、SharedArrayBuffer 和浏览器响应头要求；先检查酒馆宿主及 iframe 条件，不能直接假定可运行 |
| [elkjs](https://github.com/kieler/elkjs) | 层级图与端口排版；EPL-2.0 | 适合关系图、候选初始排位；节点排版不能直接作为米制房间及共墙门结果 |
| [polygon-clipping](https://github.com/mfogel/polygon-clipping) | 多边形交、并、差；MIT | 候选用于不规则范围、主空间扣除子空间和轮廓裁切；不负责通路、门或语义判断 |
| [Promptfoo](https://www.promptfoo.dev/docs/configuration/expected-outputs/javascript/) | 自定义 JavaScript 断言与评分；仓库 MIT | 开发侧复用现有解析器和几何检查，比较提示词输出；外部模型测试仍会向所配置供应商发请求 |
| [fast-check](https://github.com/dubzzz/fast-check) | 属性测试与反例缩减；MIT | 开发侧生成尺寸、门与家具组合，检查不重叠、锁不动、路径可达等不变量 |

本轮没有因为存在开源库就替换现有导航、Canvas 或整套布局器。应先用同一组场景比较候选算法与当前结果。

## 为什么一轮可能有多次模型调用

`atlas-work-batching.ts` 的默认计划包含：前景 1 批、建设 1 批、依据提取 1 批、地图 1 批、人物 1 批、事件结果 1 批，另有共享额外请求额度 1。各阶段按实际任务触发，不代表每轮固定发送全部批次，也不代表整轮只发一次。

| 调用来源 | 代码入口 / 触发条件 | 导出中的依据 |
| --- | --- | --- |
| 正常任务 | 前景、建设、空间依据、地图、人物、事件的调度 | `workClass`、`reason=scheduled`、目标数量、批次指纹 |
| 网络重试 | `requestSpatialWithTransportRetry`，符合可重试错误且有余额 | `reason=transport_retry`、原批次指纹、HTTP/超时结果 |
| 兼容路由 | `callAtlasWorldTurnApi` 内部特定兼容路径重发 | 同一个 `requestRef` 下多个 `transportAttempt`；实际算多次发送 |
| 依据纠错 | 摘录格式或依据验证失败，额度内重新提取 | `reason=evidence_repair` |
| 布局纠错 | 单图未返回布局、错误 JSON 或未知实体引用 | `reason=format_repair` |
| 地图补交 | 部分地图缺少结果 | `reason=missing_map_reply`，目标地图指纹 |
| 缩小合批 | 合批容量错误或截断后的缩批 | `reason=batch_split` |
| 失败组修复 | `runSqlModelRetry` | `reason=validation_repair` |
| 后台继续 | `runSqlResume`，尚有到期决策或事件待结算 | 原轮账本累计、工作类别、阶段 |
| 重复宿主入口 | 生成结束、重生成、显式重试等多次入口 | `TURN_STARTED` 与相同楼层指纹。重复入口本身不证明重复发送，必须核对发送记录 |
| 内部只读请求 | UI 刷新、状态、地图与分页读取 | `API_CALL_*`；属于插件内部调用，不直接计作模型发送 |

代码已有共享额度、批次去重、兼容重发计数与未完成地图补交。不能在没有用户逐轮记录时，直接断言十几次调用都来自同一重试漏洞。

## 已实现的逐轮分析导出

作者视角 → 诊断 → **导出逐轮分析** → 下载 `atlas-turn-analysis-*.json`。原“导出日志”按钮保留。

文件是 `atlas-turn-analysis/v1`，包括：

- 构建标识、聊天/分支/楼层指纹、修订和记录覆盖范围。
- 所有已保存轮次，包括成功、部分成功、失败与无变更；不受当前日志搜索和等级过滤影响，逐页读到末尾。
- 每轮按表与操作汇总的实际变更、组应用/拒绝数量、问题代码与可安全表示的字段路径。
- 模型传输账本：工作类别、触发原因、原批次、目标指纹、开始时间、逻辑请求耗时、HTTP/停止原因、发送和回复字符数。`logicalDurationMs` 是整次逻辑请求的时间，兼容重发时不作为单次传输独立耗时相加。
- 可用的运行事件与失败轮上下文；与数据库账本按请求指纹和发送序号对账去重。

计数规则：一次 `MODEL_REQUEST_STARTED` 是一次发送；headers/completed/failed 是后续事件，不相加；attempts 条数不是实际发送次数。旧账本与运行事件不能确定是否重叠时，合计为 null，并给有证据的下界。

新保存的轮次保留最近 256 次紧凑发送明细，完整发送总数和各工作类别总数继续累计；超出部分报告 `droppedCalls`。独立会话历史保留最近 1000 条模型/回合事件并写入 sessionStorage，关闭浏览器会话、清除日志或存储失败可能影响它，覆盖范围明确下发。界面仍使用原有小日志环，不把完整历史反复画进页面。

未保存的失败尝试不能冒充数据库已保存回合；可从尚在留存范围内的会话事件分析。旧轮次缺失的正常请求信息不能追溯恢复。导出前换聊天、分支、视角或存档修订时整份放弃，不拼接两个快照。

分析文件保留计数、标识指纹与允许的元数据；不包含 API key、连接地址、完整提示词、世界书或模型回复。代码中的固定枚举原因不进入供应商参数或用户提示词。

## 实测方式

更新本草稿后，连续运行几轮平时容易出现调用过多的场景，再导出逐轮分析文件。分析时先看每轮 `counts`、`requestAudit.byWorkClass` 与 `findings`，再看每次发送的原因及其原批次、目标是否重复，最后对照该轮的真实变更和问题代码。

本地验证覆盖实际 SQL 查询、真实模型端口的模拟 HTTP、兼容双发、预算拒绝、逻辑批次去重、旧记录未知计数、跨聊天/修订分页、重试/继续账本、会话恢复和存储失败。外部模型请求数为零；尚未据此判定用户现场的调用风暴根因。
