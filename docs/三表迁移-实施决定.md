# 三表迁移实施决定（计划 v0956 执行记录）

> 用途：记录执行《Atlas 三表迁移、推进协议替换和地图接线执行计划》时，规格与现有代码冲突处的**实际处置**。
> 每条都要能被作者否决——否决即改这里 + 对应代码与测试，不允许只改代码不记。
> 基线：`0.9.56`（HEAD `59164f2`）。本文件随里程碑推进追加，不删历史条目。

## D-01 三表行数上限保留，但镜像投影必须有界（A04 前生效）

- 规格：§1 行数初始上限 地点 1000 / 人物 2000 / 物品 5000。
- 冲突：`lib/world-schema.ts:579 maxEntityRecords = 500`、`:550 maxCharacterStates = 500`；
  `parseBoundedArray` 一超限即返回 `null` → **整份 world 解析失败**，旧档会被判损坏
  （正是 §5 停机线第一条「旧聊天丢实体」）。规格同时禁止改 `lib/`。
- 处置：三表上限按规格**不变**（`src/atlas-tables.ts` 的 `ATLAS_TABLE_LIMITS`）；
  **兼容镜像是「有界子集」投影**：人物 ≤500 条写入 `characterStates`、物品 ≤500 条写入
  `entityRecords`（按 id 排序取前 N，确定性），超出部分只存在于三表。
  实体现值的读取口径是 D01/D02（`/state` 与地图视图直接读三表），因此镜像上限不会隐藏 UI 数据。
- 影响：A04 返回的警告里必须带被截断数量；不得静默。

## D-02 物品只做「锚点镜像」，持有关系只存在于三表

- 规格：§1「按候选三表生成旧 World 所需的地点/人物/物品兼容投影」。
- 冲突：`EntityRecord`（`lib/world-schema.ts:171-185`）只有 `id/type/name/baseline/temporalSchema/mapAnchor`，
  **没有** `holderCharacterId / status / description`；`world-definition.ts:243-247` 还会校验
  `mapAnchor` 引用的点/区必须存在。且 `baseline` 的每个键都必须在 `temporalSchema` 里声明
  （`world-schema.ts:2026-2030`），未声明即整份 world 解析失败。
- 处置：物品镜像写 `entityRecords`，`type="item"`，`baseline` 只放 `description/status`（并在
  `temporalSchema` 里声明为 `kind:"base"`），持有关系**不进** `baseline`（避免被 lib 校验打回）；
  地图锚点用 `mapAnchor.pointId`。D01/D02 读物品与持有关系一律走三表。
- 影响：「随身物品」必须由地图视图按持有人位置临时推导（§1 允许），不得持久化重复坐标。

## D-03 画布坐标 → 格序号的换算口径：1 画布单位 = 1 格（A03 已实现，A04 反向同口径）

- 规格：§1「旧 `world.points[].x/y` 是画布坐标，必须经 frame/cellPx 转换」「找不到 frame 的旧点保留位置未知」。
- 实测口径（三处互相印证）：
  1. `lib/world-schema.ts:2040-2041` 对 `entityRecords[].mapAnchor.x/y` 硬性要求 **0..100**；
  2. 子图布局空间本来就是 0..100（`atlas-geo-apply.ts` 的黄金角布点把坐标夹在 4..96）；
  3. 世界图 frame 与子图默认 frame 同为 100×100（`atlas-server.ts:2560`），且标尺调用
     （`index.js:2028` 用 `cellPx: camera.k, zoom: 1`）等价于 `metersPerPixel = metersPerCell / k`，
     即 **1 画布单位 = 1 格**；style.css 里 27px 的网格线只是显示用格线，不是换算基准。
- 处置：
  - 根地点：`gridX = round(x)`、`gridY = round(y)`；**不做最小坐标归一化**（归一化会让坐标脱离
    0..100 口径，并使第一次往返整体平移）。
  - 负坐标**不夹到 0**（那等于把地点挪到原点）：按位置未知处理（`gridX/gridY = null`）+ 警告。
  - 子地点：父图 sidecar 布局坐标本身就在子图自有的 0..100 格空间 → 直接 `round`；
    父图没有该点的布局记录 → 位置未知 + `SUBMAP_LAYOUT_MISSING`。
  - A04 反向：`x = gridX`、`y = gridY`（同口径直取），因此 `world → 三表 → world → 三表`
    **第一次往返就是不动点**（格序号不再变化）。格序号 >100 的点仍允许存在（frame 只是默认值），
    但镜像的 `mapAnchor` 会因 lib 的 0..100 上限省略 x/y。
  - 位置未知的行在镜像里必须仍有点位（否则引擎看不到该地点）：优先沿用基底世界的画布坐标，
    否则落在父地点坐标（子地点）或 (0,0)（根地点），并记 `POSITION_DERIVED`。
    **镜像不得当作迁移输入**——迁移只在 `tables` 缺失时发生一次（A08 保证），否则派生坐标会在
    下一次迁移里被误当成真实坐标。

## D-04 v1/v2 协议分流保留，新协议默认关闭（C02/C04 前复核）

- 规格：§2「协议选择只由 `settings.worldTurnProtocol` 控制，新增 `table-delta-v1`」「彻底移除靠响应全文 regex 猜 v2 的分流」。
- 现状：`src/atlas-server.ts:2244` 用 `/\"schemaVersion\"\s*:\s*2/` 扫全文决定走 v2（0.9.53→0.9.56 实测最脆弱的一处）；
  `worldTurnProtocol` 现有联合类型 `"v1" | "v2"`，默认 `"v2"`。
- 处置：C04 移除全文正则分流，改为按设置值精确分派；`table-delta-v1` 只在用户显式切换或
  里程碑 4 验收通过后才作为**新装默认**；既有自定义提示词预设不自动改写。

## D-05 行 id 方案（A03/A04/B04 共用）

- 规格未指定 id 形态；为让镜像可逆，统一为 `loc:<world.points[].id 数字>`、
  `npc:<world.characters[].id 原文>`、`item:<world.entityRecords[].id 原文>`，
  由 `src/atlas-tables.ts` 的三个构造函数产出，禁止各处手拼前缀。

## D-06 「非 NPC 物件」需要一份非物件类型表（A03 已实现）

- 规格：§3-A03「`entityRecords` 中非 NPC **物件**→物品」。
- 风险：按字面理解成「非 NPC 即物品」会把势力 / 城市 / 地区类实体迁成物品行，
  随后 A04 镜像把它们改写成 `type:"item"` 写回 `world`——**静默的数据损坏**
  （本仓库的 chronicle 夹具里就有 `type:"faction"` 的实体，测试直接把它逼出来了）。
- 处置：`src/atlas-table-migration.ts` 维护 `NON_ITEM_ENTITY_TYPES`
  （faction / organization / group / guild / clan / party / city / region / nation /
  country / realm / location / place + 中文同义），这些实体**不进三表**，
  由 A04 原样透传；表里未列出的类型仍按物件处理（作者自定义物件类型不受影响）。
- 影响：作者若用自定义类型登记物件且该类型恰好在上表里，需要改名或扩展常量。

## D-07 镜像的已知有损字段（A04 已实现，测试显式断言）

| 字段 | 镜像行为 | 原因 |
| --- | --- | --- |
| 物品 `holderCharacterId` | **丢弃**（持有物仍无地点、无锚点） | `EntityRecord` 没有持有人字段，且 baseline 键必须已声明（D-02） |
| 人物 `presence="left"` | 不写 `currentPointId`，记 `PRESENCE_NOT_MIRRORED` | `CharacterState` 没有 presence 字段；写位置等于说「他还在这」 |
| 人物 `thought` / `actionTendency` | 只把 `currentAction` 写进 `status` | `CharacterState.status` 是唯一的文本槽位 |
| 地点 `gridX/gridY = null` | 沿用基底世界坐标，否则父地点坐标 / (0,0)，记 `POSITION_DERIVED` | 镜像是引擎的可读投影，需要有点位；真值仍以三表为准 |
| 人物档案 `world.characters` | **不改写** | 档案是作者资产；三表名字由 D01/D02 直读呈现 |

因此 `world → 三表 → 镜像 → 三表` 只在**可镜像字段**上是不动点（地点全等、人物全等、
物品除持有人外全等），这条已写成测试断言，不靠口头约定。

## D-08 三表快照的分支键：`branchKey = branchScopeForStory(...) ?? "canon"`（A08 已实现）

- 规格：§1「`branches[branchId]` 是该分支三表快照」。
- 现状：绑定里的 `binding.branchId` 可能是**正史故事线 id**（`mode === "canon"`，例如 `chronicle-canon`），
  而不是 null；直接拿它当键会让「正史基线」在不同聊天里出现两个键。
- 处置：用 `branchScopeForStory(world, binding.branchId)` 归一：正史线 / 未知故事 → `null`；
  IF → 该 IF 的 story id。`null` 落为保留键 `"canon"`。
  万一某个 IF 的 story id 恰好是 `canon`（会与基线冲突），**拒绝迁移**并记
  `TABLE_BRANCH_KEY_RESERVED`，不猜、不覆盖。

## D-09 懒迁移的落盘时机：先挂到会话对象，是否落盘交给原有 `overlay.changed()`（A08 已实现）

- 规格：§3-A08「对真实旧会话懒迁移……迁移失败不覆盖 session」。
- 第一版实现（**已被测试否决**）：迁移经 `overlay.write("tables:<worldId>", …)` 落进会话。
  后果是任何**只读**请求（GET /state、`/scene/repair-start` 的只读检查）都会把 `overlay.changed()`
  置真 → 响应推 `rev+1` → 撞上既有不变量「只读检查不写会话」
  （`tests/atlas-r06-scene.test.mjs:357` 直接断言 `carrier.session.rev` 不变），全量测试红。
- 处置：迁移成功后**直接把结果挂到会话对象**（`session.tables = …`），不调 `overlay.write`：
  - 本次请求的 engine 侧经覆盖层 `tables:<worldId>` 正常读到三表；
  - 只读请求因此不推 rev、不写 `chatMetadata`（不变量保住）；
  - 任何真正的写请求（回合提交、绑定、场景…）本来就会 `changed()`，
    带三表的会话随同一次响应回到浏览器落盘——迁移不会丢。
- 代价：若某个聊天此后始终只读，三表只活在内存里；但那种情况下世界也没有任何变化需要持久化。
- 迁移仍是确定性的（A03 纯函数），响应被切聊天守卫丢弃时重复迁移不产生新行或新 ID。

## D-11 `index.js` 改动必须同步镜像再 pack（本轮实测被 P0-01 用例拦下）

- 事实：`atlas-extension/index.js` 是根 `index.js` 的**人工同步镜像**，唯一有意差异是 dev 回退行
  （`const attempts = [..., "../src/atlas-ui-core.ts"]`）；`tools/pack.mjs:114-125` 会用
  「剥离该行后逐字相等」断言两者一致，不一致直接抛错。
- 本轮 A07 改了 `index.js` 却没同步镜像 → `tests/atlas-integration.test.mjs:187`（P0-01）失败。
- 处置（同时也是后续所有 `index.js` 改动的收尾步骤）：
  1. `node tools/pack.mjs` 的报错即为提醒；
  2. 同步口径 = 复制根 `index.js` 覆盖镜像，再把打包行换回 dev 回退行
     （本轮用临时脚本 `%TEMP%\atlas-sync-mirror.mjs` 完成，并自检 strip 后逐字相等）；
  3. 再跑 `npm run pack`：它会重建 `atlas-extension/dist/atlas-ui-core.mjs`、
     `atlas-server-plugin/dist/atlas-server.mjs`，并把 release 的 dist 刷回根 `dist/`。
- 结论：**改了 `index.js` 或 `src/` 就不算跑完——必须 build + pack 之后再跑全量测试。**

## D-10 顺带修复：会话覆盖层 `read()` 里的一段不可达代码（A06）

- 原实现中 `read()` 有两段 `if (name.startsWith("scene:"))`：第二段整体不可达
  （第一段已 return），且内容是**清空 scene 的写逻辑**被误粘进读路径。
  一旦将来有人调整前一段的返回条件，读操作就会「顺手清场景」。
- 处置：A06 删掉不可达段（行为零变化），保留原有只读回退语义；同一提交里补上 `tables:` 分支。

## D-12 B01–B04 的行为处置（删除语义、保护范围、深度常量）

- 规格原文只给了方向（§2「remove 只用于正文明确消失/销毁，默认软删除或撤离，不能级联删地点和人物」），
  具体语义由本轮定死如下，三条都有测试断言：
  | 操作 | 语义 | 理由 |
  | --- | --- | --- |
  | 地点 `remove` | **有子地点直接拒绝**；无子则删行，并把引用它的人物 / 物品归属**就地置空** | 拒绝级联是规格原话；置空是必须的——留着 `locationId` 会让候选表带悬空引用，整轮被 A01 判死 |
  | 人物 `remove` | **撤离**：`presence="left"`、位置与目标清空、行保留 | §2「默认软删除或撤离」 |
  | 物品 `remove` | **软删除**：状态置 `ATLAS_ITEM_DESTROYED_STATUS`（"已销毁"）、归属清空、行保留 | 同上；D01 的投影口径按「无归属且已销毁 → 不进地图 / 面板」过滤 |
- **主人公保护范围**：`options.protectedCharacterIds` 里的人**名称不可被模型改写、整行不可被 remove**；
  想法 / 行动倾向 / 当前位置仍可更新（否则主角根本走不动路）。判定依据由调用方从
  `world.characters[].role`（`isProtagonistRole`）算好后传入——三表本身不存 role（契约固定）。
- **地点深度常量**：B01 用 `SUBMAP_DEPTH_MAX`（`src/atlas-geo-apply.ts`，地图侧权威）。
  仓库里同一个 4 另有一份 `V2_SUBMAP_DEPTH_MAX`（`src/atlas-turn-v2.ts`，被提示词文案引用）——
  **两处重复待合并**（属 C/D 段收口，本轮不动 v2 以免超出一个编号的范围）。
- **子图生成**：B01 不「生成子图」——`mapId = 父行 id` 之后由 D01 的 `projectWorldSubmaps`
  口径在读取时派生（§1「不另存 children 数组」）。

## D-13 `parseAtlasEditBlock` 的第二参数取 sources 记录（B05）

- 规格签名写的是 `parseAtlasEditBlock(text, sourceText)`（单个字符串）。
- 但 §2 同时要求「`quote` 只需要直接包含在助手正文或用户正文之一，**程序决定 sourceId**」——
  单个字符串无法分辨引文来自哪一侧，也就无法回执 `sourceId`。
- 处置：第二参数取 `{ "msg:u"?: string; "msg:a"?: string }`（与 v2 同一套 sourceId）；
  命中优先级 msg:a → msg:u，结果写在每行的 `sourceId` 字段上。

## D-14 判定顺序与依赖传播（B05/B06）

- **根因优先**：同一行同时违反「inferred 无权改这个字段」与「缺引文」时，报
  `INFERRED_FIELD_NOT_ALLOWED`（依据类型错），而不是 `QUOTE_REQUIRED`——后者会让模型以为补个引文就行。
- **本块依赖检查覆盖所有引用槽位**：不只 `ref`，`parentRef / locationRef / holderRef / targetLocationRef`
  及其 `patch` 版本里凡是 `new:*` 的，都必须是本块**前面已接受**的新增行；否则该行记
  `DEPENDENCY_FAILED`（不整轮失败，§2）。
- **零有效行时块级错误取第一条真实原因**（例如某行超长 / 引文不匹配 / 语法错），而不是笼统的
  `NO_VALID_EDIT_LINES`——否则回执会掩盖具体字段路径，C08 的诊断也就没用了。
- 解析期只做**块内**依赖与形态校验；正式行 id 是否存在由 B06 对候选表判定（解析器没有表）。

## D-15 `isV2ProtocolEnabled` 收紧为「精确等于 v2」（C02）

- 原实现是 `protocol !== "v1"`——语义上「不是旧协议就是 v2」。
- 加入 `table-delta-v1` 后这个判定会把新协议**误判成 v2**，于是内置提示词装成 v2 封套、
  模型按封套输出、解析器按行增量解析 → 必然 `PROTOCOL_MISMATCH`（而且症状会伪装成"模型不听话"）。
- 处置：`isV2ProtocolEnabled(protocol)` → `protocol === "v2"`；新增
  `isTableDeltaProtocolEnabled(protocol)` → `protocol === "table-delta-v1"`。
  调用点（`atlas-server.ts` 的 `prepareWorldTurnInputs`）本来传的就是
  `settings.worldTurnProtocol ?? "v2"`，因此对旧配置零影响。
- 同时把 `worldTurnProtocol` 的联合类型收敛成 `AtlasWorldTurnProtocol` 一处定义 +
  `normalizeWorldTurnProtocol()` 一个归一函数，避免五处各写一遍 `"v1" | "v2"`。

## D-16 新协议默认值保持不变（C02，按计划 §2）

- §2 明确「切换前先让三表迁移及读图通过验收，再将新安装默认改为 `table-delta-v1`」。
- 因此本轮**只**让 `table-delta-v1` 变成合法可选项（runtime.update + sanitize + 视图回显 +
  内置分段展示 + 新建预设快照），默认仍是 `v2`；默认切换留到里程碑 4 验收通过后单独一步。
- `defaultSegmentsForProtocol()` 是「内置默认分段随协议展示/快照」的唯一入口，
  三个协议段位都是 6 段（索引 0 = 协议段 mainSlot A、4 = 本轮行动 mainSlot B、5 = 核对段），
  bootstrap 模式才能继续按同一索引替换第 5 段。

## D-17 ⚠ 需要作者裁决：协议分流「按设置」与「混合模式」直接冲突（C04 只做了一半）

- 计划 §2 原文：「协议选择只由 `settings.worldTurnProtocol` 控制……**彻底移除**靠响应全文 regex 猜 v2 的分流」
  「若输出协议与选择不符，报 `PROTOCOL_MISMATCH` 并指明当前选项，**不偷偷落回 v1**」。
- 但仓库公开文档（`IMPLEMENTATION_STATUS.md:302`）承诺的是相反的行为：
  「作者自定义预设不被覆盖（**混合模式：v1 输出仍走 v1 管线**）」——即设置是默认值，
  实际管线由模型输出的**形态**决定。
- 本轮实测：把分流改成"严格按设置"后，**20+ 既有用例立刻变红**
  （它们都是默认 v2 设置 + v1 形态草稿的老链路，例如 `tests/atlas-server-plugin.test.mjs:500` 的
  「commit：恰好 1 请求、原子落账、绑定游标推进」）。也就是说，严格执行 §2 会**静默改变现有用户的行为**：
  所有还在用 v1 形态提示词的作者，下一次提交会从"能提交"变成"PROTOCOL_MISMATCH 失败"。
- 本轮处置（不做静默破坏）：
  1. `table-delta-v1` **严格按设置**分流（新协议没有历史内容要对账，输出不是完整行增量块就明确失败）；
  2. `v1` / `v2` 维持既有混合模式（设置是默认，内容形态决定管线），但**新增具名诊断**
     `world-turn-protocol-mismatch`（`reasonCode = SETTING_V1_TEXT_V2 / SETTING_V2_TEXT_V1`）——
     旧实现是无声无息，现在不匹配一定留痕；

## D-24 E05：回退用「回合前三表快照」而不是重新迁移（快照 + 重建双路径）

- 规格：§3-E05「回退到检查点/旧楼层时对应三表一起还原；旧检查点没有 tables 则从**回退后的**可见世界重建；
  重试同一消息不会累加物品、NPC 位移或时间」。
- 实测缺口：`handleRollback` 原本只回退 `world` + `binding`。三表留在"未来"，
  于是 §5 停机线「回退后地图不一致」成立：地图回到过去、三表还在未来。
- 处置（两条路径，都有用例）：
  1. `commitTableDeltaTurn` 提交时把**回合前三表**深拷贝进回合映射 `tablesBefore: {branchKey, tables}`；
     回退优先取它（`TABLES_ROLLED_BACK`）——瞬时、精确，不依赖任何重推导；
  2. 老回合没有该字段（行增量之前的回合）→ 用**回退后的世界**重建一次（`TABLES_REBUILT_FROM_WORLD`），
     口径与 A08 懒迁移完全一致（可见世界 + maps sidecar + 分支作用域）；
  3. 重建失败 → 世界回退照常生效，但**明确抛错**（`SESSION_STALE`）并记 `world-turn-table-rollback` 诊断，
     绝不静默留下半状态。
- 只在该分支本来就有三表时写回（`priorDoc.branches[branchKey]` 存在，或本轮带了快照）：
  没有三表的旧聊天不会因为一次回退凭空长出三表（`store.read` 读不到就跳过）。
- 快照的序列化按 `JSON.parse(JSON.stringify(...))` 判定——快照要进 `chatMetadata`（浏览器持久化），
  不能带不可序列化引用；判定不过就退回重建路径，不写坏文档。

## D-26 E03/E02/E01/E04：旧写入口改世界后**加法合并**进三表（`syncBranchTablesFromWorld`）

- 规格：§1 唯一写入规则 + §3 E01–E04「每一个入口都调用同一转换器同步三表并做一致性检查」。
- 实测缺口：`/worlds/move-author`、`/worlds/geo/adopt`、`/scene/bootstrap` 只写 `world`。
  行增量回合只读三表 → **作者的拖动纠偏会被下一回合静默回退**（拖了、地图动了一下、下一轮又回去）；
  地理提炼出来的新地点同样"地图不长、模型引用不到"。
- 处置：新增一个共用转换器 `syncBranchTablesFromWorld({store, binding, world, source})`，
  四处调用（move-author / geo-adopt（手动+首轮自动）/ scene.bootstrap），回执都带 `tables: {status, reasonCode, added, moved}`。
- **为什么是"加法合并"而不是整体重投影**（这条最容易做错）：
  `thought` / `actionTendency` / `presence` / `positionSource` / 物品持有人与状态**只存在于三表**，
  A04 的镜像里没有这些字段（D-07）。整体重投影 = 用镜像覆盖真值，一次拖动就会把这些事实抹成空。
  因此合并纪律是：
  | 情况 | 处置 |
  | --- | --- |
  | 世界里**新出现**的地点 / 人物行 | 追加进三表（地理提炼、纠偏顺手建档靠这条） |
  | 已有行、位置四元组确实变了 | 只更新 `locationId/mapId/gridX/gridY/positionSource`（拖动纠偏的落点） |
  | 已有行、其余字段 | **原样保留**三表现值（不覆盖、不推导） |
  | 该分支还没有三表 | 什么都不做（`TABLE_BRANCH_MISSING`；旧会话由 A08 懒迁移按同一份世界建立） |
  | 合并后不过 A01 | 不动三表、记诊断（绝不把坏快照写进会话） |
- 已知副作用：`added.locations` 会把"世界里存在但三表里没有"的行都补进来（例如首轮自动建图那一路径
  在行增量回合之后跑，会把镜像里的行补进表）。因为只增不覆盖，不会破坏真值；
  但**它意味着"三表 = 某分支实体现值"这条纪律，在这些旧入口上退化成"三表 ⊇ 世界镜像"**。
  彻底版（E02 要求：提炼经地点表写入、再生成镜像）留待后续编号；本轮先把"静默回退"这条止血。

  把 `tests/atlas-server-plugin.test.mjs` 里的中文写成了乱码（930 个 U+FFFD），
  随后 `git diff` 显示 864 插入 / 608 删除——**完全不是一次字符串替换该有的规模**。
- 处置：`git checkout --` 恢复该文件，用 Node 脚本 / 编辑工具重做改动（其余三个被点到的
  测试文件检查后无损伤：乱码计数为 0）。
- 纪律（写下来避免重犯）：
  1. 改仓库里的文本文件一律用编辑工具或 Node 脚本（`readFileSync/writeFileSync` 显式 utf8）；
  2. 用 PowerShell 时必须 `[System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8)`
     + `WriteAllText(..., UTF8Encoding($false))`；
  3. **改完先数字符长度与乱码计数，再看 `git diff --numstat`**——插入/删除行数明显超过预期就是出事了。
